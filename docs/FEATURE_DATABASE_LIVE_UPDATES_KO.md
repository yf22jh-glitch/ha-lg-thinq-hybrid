# 기능 DB 변경의 실시간 적용

`my_lg_features.sqlite3`의 커밋된 변경을 2초 간격으로 확인하고, 바뀐 엔티티만
실행 중인 플랫폼에서 추가·제거·교체한다. DB 수정으로 통합 전체를 재로드하거나
Home Assistant를 재시작하지 않는다. 이 코드를 처음 설치할 때의 코드 로딩은 별개다.

## 변경 가능한 것

| DB 항목 | 실행 중 반영 |
|---|---|
| `features.enabled` | 읽기 엔티티의 추가·제거, 제어 기능의 허용·차단 |
| 읽기 정의의 `labelKo` | 표시 이름 변경 |
| 제어 정의의 `labelKo` / `label_ko` | DB 관리 제어 엔티티의 이름 변경 |
| 제어 정의의 `valueMappings[].homeAssistantValue` | DB 관리 select의 선택지 표시 문구 변경 |
| `valueMappings[].localRequestValue`, `supportedValues` 등 | 이미 구현된 명령의 값·연결 정의 변경 |
| 이미 발행되는 읽기 필드의 새 정의 | 엔티티 생성, 수용한 현재 메시지에서 호환되는 값 복구 |
| 주석·출처·검증 기록 | 관리 정보만 변경; 엔티티를 다시 만들지 않음 |

`runtimeHandler`를 지정한 기능은 브리지의 교체형 `.mjs` 파일이 해독·명령 생성을
맡는다. HA는 파일을 실행하지 않고 엔티티 정의만 읽는다. 새 처리 로직이 필요하면
그 파일과 DB 정의를 함께 넣으며 이후 파일 교체에도 HA 재시작은 필요 없다.
기기 연결·명령 전송·에너지 적산 같은 고정 실행부 변경은 코드 배포가 필요하다.

설명 문구를 수정한다고 새 패킷 처리 코드가 생성되지는 않는다. 표시 문구와
명령값은 분리돼 있다. 예를 들어 선택지 표시를 `high`에서 `강풍`으로 바꿔도
명령은 기존 `localRequestValue: high`로 전송한다. 알려지지 않은 명령·원시값은
추측해서 제어하지 않는다. Native PAT/WideQ 카드 자체의 선택지 정의는 별도이며,
그 카드의 문구 변경과 DB 관리 select의 선택지 변경을 혼동하지 않는다.

## 유지되는 것

- MQTT 연결, 현재 접속 세션, 수용한 메시지 순번 및 명령 라우터를 유지한다.
- 바뀌지 않은 엔티티 객체와 에너지 적산 상태를 유지한다.
- `unique_id`와 엔티티 레지스트리 행을 유지하므로 이름을 바꿔도 이력은 이어진다.
- HA에서 사용자가 따로 비활성화한 엔티티를 DB 변경으로 강제로 켜지 않는다.
- DB 비활성화는 실제 제어도 차단한다. 확장 선언이나 Native 클라우드 별칭으로
  같은 제어를 되살리지 않는다. 이미 전송한 명령을 취소한다는 의미는 아니다.
- 제어 기능의 새 엔티티는 DB에서 활성화돼 있으면 기본 활성으로 추가한다.
  기존 HA 레지스트리의 비활성 설정은 그대로 존중한다.
- 읽기 기능을 꺼도 원시 캡처와 이미 등록된 생산자 데이터 수집은 중단하지 않는다.

비활성화된 읽기 엔티티는 실행 플랫폼에서 제거되며 레지스트리와 이력은 남는다.
HA 레지스트리 화면에는 미제공/unavailable 항목으로 남을 수 있다. 재활성화하면
같은 ID로 돌아온다. 단위·값 타입이 바뀌면 예전 값을 새 단위로 재해석하지 않고
호환되는 새 값이 올 때까지 미상으로 둔다. 이벤트 메시지는 재실행하지 않는다.

## 운영 방법

기존 `scripts/manage_local_features.py`의 `enable`, `disable`, `upsert`를 사용한다.
SQLite로 직접 수정한 커밋과 WAL 모드 커밋도 감지한다. 여러 필드를 함께 바꿀 때는
하나의 트랜잭션으로 커밋해야 중간 설정이 적용되지 않는다.

`control-entity`와 `confirmed-control` 양쪽에 있는 같은 모델·기능은 어느 한쪽의
비활성화도 우선한다. 다시 켤 때는 같은 기능의 모든 선언을 활성화한다.
읽기는 `full-read` 정의가 있으면 그 활성 플래그가 표시 여부의 기준이다.
정식 읽기를 숨겼을 때 보조 경로로 되살아나지 않는다. 정식 정의가 없는 항목은
`pilot-read` 플래그를 사용하며 어느 경우에도 내부 수집은 유지한다.
`model_rollout.enabled=0`은 기능 끄기가 아니라 기존 번들 정의로 되돌리는 옵션이다.
접속용 `pilot-profile`을 지우지 말고 그 안의 기능 필드를 관리한다.

로그 `Local feature database applied live`에 추가·제거·변경 개수가 남는다.
DB 모델의 `confidence` 근거 문구는 진단 정보다. 해독 파일을 바꿨다고 예전
문구 허용 목록에 맞추거나 계약 버전을 바꾸지 않는다. 값 타입·단위·기기 구분과
문구의 기본 형식은 계속 확인한다.
DB 읽기나 적용 실패는 로그를 남기고 다음 확인에서 재시도한다. 성공 전에 변경을
소비한 것으로 표시하지 않는다. 비교용 토큰은 변경 감지용 캐시 키일 뿐이며,
릴리스·기기 계약 세대·과거 원장과 비교하는 수용 게이트가 아니다.

## 테스트

`tests/test_feature_runtime.py`와 `tests/test_feature_database_watcher.py`에서 직접 SQL
변경, 새 필드 추가, 이름·선택지 변경과 실제 명령값 연결, 비활성 제어 차단,
재활성화, 사용자 비활성 보존, 잘못된 단위 재해석 방지, 에너지 객체·누적값 유지,
실패한 언로드 후 변경 재개 및 통합 재로드 호출 없음까지 검사한다.
